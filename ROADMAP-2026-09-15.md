# GRIDRUNNER — current + new implementation pipeline

Captured from the user's September 15 notes and follow-up requirements. The Three.js game on `grok` is the target of this update; Godot, Unreal and approved Blender originals are unchanged. Status below distinguishes implementation from design intent.

## Foundation: implemented, still requiring field QA

- v7.15: Rapier collision and Recast camp routes.
- v7.16: broader world collision, sweeps, fleet hotkeys, Wedge/Trail/Line/Orbit formations.
- v7.17: weight/class/load-sensitive flight, fast Scout/Relay, shared dual-stick controls, Flight Yard cargo load and mass telemetry.
- v7.18: stable aircraft/onboard-battery identities, persistent task lifecycle and a real survey → scan → return sortie. Individual and fleet commands interrupt jobs consistently; saves retain ownership/progress, safety failures take priority, and Flight Yard remains isolated.
- Automated checks do not prove every world mesh has a correct collider. Continue testing fast drones and rider/bike against terrain, trees, rocks, roofs, gates and props. Aircraft-specific collision hull dimensions remain a separate refinement; v7.17 retains the existing hull sweep shape.

## 1. Fleet task and ownership foundation — first slice implemented in v7.18

Introduce task records and explicit aircraft/battery ownership before long-lived autonomous energy jobs. Preserve manual flight, commands, emergency landing, reserve-return logic and safe saved-state recovery.

Implemented: one SURVEY job per existing airframe, unique monotonic job IDs, aircraft/battery references, fixed waypoint, transit/survey/return stages, running/paused/completed/cancelled/failed states, elapsed time, at-most-once scan/debit, reason reporting and Fleet pause/resume/cancel controls. FPV takeover pauses work and resume restores the rider's prior position. The battery ID refers to the existing onboard percentage resource; it does not create a spare pack or duplicate charge. Jobs run during resumed gameplay only, never offline.

The first-slice acceptance below is covered by automated simulation and full-module tests. Still deferred: generalized task queues, swappable battery assets, campaign drone payload inventory and multiple instances of a class. The current job observes/scans; it neither harvests nor transports energy.

- Current fleet is one instance of each of four airframe types. Multiple same-class harvesters will require stable instance IDs and a migration from class-keyed squad records; do not fake this with shared state.
- Tasks need assignment, active stage, destination, payload/battery ownership, pause/cancel, failure reason and resume after load.
- All aircraft use the same mass/flight model; autonomous movement must not teleport or bypass collision.
- Minimal first acceptance: an aircraft can be assigned, interrupted for manual control, recalled, saved and restored without duplicating payload or losing the rider's position.

## 2. Physical power-line perch and recharge — next gameplay slice

The user specifically wants physical perching on energized conductors, inspired by the supplied SDU-style references. It is **not** a generic proximity-energy aura and not limited to the existing authored receiver platform. The old receiver mechanic is still present; it is not this new system.

- Find reachable points along live transmission/distribution spans; allow perching anywhere valid on a supported span, not only a premarked station. Account for sag, clearance and occupied positions.
- State sequence: LINE DETECTED → ALIGN → PERCH → COUPLING → CHARGING → RELEASE. Drone aligns and grips the line, stops propulsion, charges while attached, then safely detaches before flight.
- Show line status, charging rate, estimated time, signal and interference. Dead lines produce no energy and encourage tracing/restoring the network. Prevent duplicate energy accounting and recheck line state after load.
- Keep electrical engineering abstract and fictionalized. This is game behavior, not real-world instructions for contacting power lines.

## 3. Harvesters, batteries and trailer logistics

Acquire or build multiple harvesting drones. Fly them out manually or dispatch them; leave them perched until needed. They charge their own batteries and removable carried packs, return stored energy to the trailer, unload and redeploy.

- Model charged packs, energy capacity, charge, mass and ownership explicitly. Current aircraft return to the **bike**; the future trailer unloading destination must be implemented, not assumed to exist.
- Independent deployed drones persist through saving/loading. Only eligible equipment can lift a pack. Returning with heavy packs uses loaded flight and reserve estimates.
- No duplicated or disappearing packs when switching aircraft, docking, changing tasks, interrupting a return or reloading a save.

## 4. Autonomous fleet / power-management layer

The user wants a system-management game underneath exploration, combining scouting, relay coverage and harvesting:

- Harvest → charge to 90% → return → unload → redeploy.
- Scout → discover a live corridor → establish relay → harvest while idle.
- Maintain trailer reserve above a configurable threshold (example: 40%).
- Leave a charged drone/pack in place until recalled; choose between charge stockpiling and transport.
- Recall or hold safely when weather, interference, weak signal, damage or insufficient return energy threaten the task. Show why a task cannot proceed.
- Fleet view reports current jobs, reserve, generation, consumption and estimated return times. Policy thresholds are examples, not finalized balance settings.

## 5. Original CODEC communicator + authored introduction

MGS-inspired portrait/radio interaction grammar, with original GRIDRUNNER artwork, voice, layout and terminology. Do not copy Metal Gear character likenesses, dialogue, audio or exact UI.

- Portrait-to-portrait calls introduce Mara and other contacts; carry discoveries, warnings, tutorials and story beats through a consistent communication interface.
- Design the intro as one authored sequence combining story, audio/narration, cinematic/video treatment and playable tutorial pacing.
- Rework bike, trailer and SCOUT acquisition lessons together. Keep the object being explained visible; avoid covering it with the tutorial panel or duplicating HUD layers.
- Mute/skip/replay, subtitles, reduced motion, interruption handling and save-safe progress are requirements. Optional calls should allow movement; essential teaching beats may deliberately pause, with clear controls.
- New communication presentation replaces relevant overlay clutter; it is not another permanent full-screen overlay. Existing recorded narration has not been replaced in v7.17.

## 6. Eclipse world state

Selectable and potentially rare event with distinctive sky/lighting, reduced solar generation, temperature/atmosphere changes, navigation visibility and authored NPC/wildlife/radio responses. Stored energy and live lines become temporarily more valuable.

- Existing night/blackout/weather modes are not an eclipse. An actual eclipse needs a time/state envelope and matching energy behavior.
- Use one shared solar-availability value for visuals and every solar generator; no sunlight-independent solar charging during totality.
- Save event phase and test entry, totality, exit, pause/resume and reload. Sensor/interference anomalies and special story clues are design possibilities, not implemented behavior.

## Guardrails for every slice

Run the full regression suite; add tests for each new state transition, interruption and save migration. Keep campaign and Flight Yard separate. Protect existing assets, games and branches. Be explicit about what has been committed, pushed or deployed: those are different operations.
